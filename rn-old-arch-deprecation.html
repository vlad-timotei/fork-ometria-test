Ometria RN SDK — New Architecture & SPM Migration Plan

Where we stand, what's blocking us, and what to do next.

Our SDK 4

Ometria iOS SDK (native) — SPM support

Ready
Already compatible with the new iOS packaging. Old packaging also works.
Why this matters

The iOS SDK ships a Package.swift file (in v1.8.9, the version we depend on) — meaning the prerequisite for switching the React Native SDK to SPM is already done. The native SDK pulls FirebaseMessaging via SPM directly, so we're not affected by Firebase dropping CocoaPods in October 2026.

Ometria RN SDK — Expo support

In review
Next release adds Expo support. Code is in review, awaiting publish.
Detail

Currently published v2.7.1 (March 2026) supports both architectures. The next release v2.8.0 (on the release/2.8.0 branch) adds the Expo plugin and an Expo sample app. Expo SDK 55, already released, is new-architecture-only — so this is the supported path for Expo customers going forward.

Ometria RN SDK — SPM mode

Blocked
Cannot release yet. Blocked by React Native Firebase needing to update first.
Why blocked

The SPM mode requires dynamic framework linking. Current React Native Firebase (v25) still mandates static framework linking. CocoaPods only allows one linkage setting per project, so both can't coexist. Shipping the SPM version today would break every client who also uses React Native Firebase — most of our customer base.

We can prepare it on a branch and validate it against React Native Firebase's preview branch, but cannot release until they unblock it.

Ometria — old architecture support

Through Q3 2026
React Native walked away from it, but we still support old-architecture clients. Any release we ship through end of Q3 2026 will support old architecture. After that date, new releases drop it.
Timeline & client impact

Where it stands upstream: React Native froze old architecture in June 2025. Version 0.82 (October 2025) removed the option to disable the new architecture. Clients on old architecture are pinned to React Native 0.81 or older, and that version is itself now unsupported by the React Native team.

Our position: the currently published Ometria SDK (v2.7.1) supports both architectures. Any release we ship through end of Q3 2026 will continue to support old architecture — chosen as the cutoff because it's before Firebase stops publishing to CocoaPods in October. After that date, any new Ometria release drops old-architecture support. If we don't ship anything new between now and the end of Q3 2026, then whatever is currently published (v2.7.1 today, or v2.8.0 when it lands) remains the working version for old-architecture clients.

What clients keep: their existing app and any Ometria SDK release up to our final old-architecture-supporting version continue to work. They lose access to new SDK features, and they cannot update Firebase/Google Maps on iOS after October 2026.

External dependencies 4

React Native Firebase — SPM support

In review
Their fix is in active review. Maintainer plans to merge. Some items still open.
Status detail

PR #8933 — dual-mode design: SPM by default on recent React Native, CocoaPods as fallback. The SPM mode uses dynamic framework linking, which is exactly what our SPM path needs — so the endpoints are compatible.

Opened March 17, 2026. Maintainer (Mike Hardy): "Wow! This is pretty amazing… we [will] merge SPM support." External contributor, so timeline depends on review cycles. Realistic ETA: weeks to a few months.

React Native — full SPM move

Not shipped
React Native hasn't shipped this yet. The cleanest setup waits on it.
Why this matters

Until React Native itself ships as a Swift Package, every project still needs a Podfile and a global linkage decision. The interim SPM-mode migration moves us from static to dynamic linking — a big win — but the cleanest endpoint (no linkage decision at all) waits for this. React Native 0.84 (Feb 2026) was a major preparatory step. 0.85 (April 2026) did not yet land it. Expected later in 2026.

CocoaPods — the iOS package system

Sunsetting
Shutting down. Hard cutoffs in October and December 2026.
What changes

Existing package versions stay installable; deployed apps keep working. After October 2026, no new Firebase versions on CocoaPods. After December 2, 2026, no new packages can be published to CocoaPods at all, anywhere.

React Native — old architecture

Dropped
Dropped by React Native in June 2025. No security updates from upstream. Does not compile on Xcode 26 out of the box — and Xcode 26 has been required by the App Store since April 28, 2026.
Why it doesn't compile, and what it would take to fix

The React Native team froze old architecture in June 2025 — no new features, no bug fixes, no security patches. Version 0.82 (October 2025) removed the option to disable the new architecture. Version 0.81 was the last release that ran on old architecture, and it is itself now unsupported.

The Xcode 26 build wall (active since April 28, 2026). Apple now requires every App Store submission and update to be built with Xcode 26 + iOS 26 SDK. Xcode 26 has multiple confirmed build failures with React Native: FMT consteval errors, ReactCodegen module errors, constexpr with Objective-C literal issues, and most critically — Xcode 26's explicit module scanner ignores CocoaPods' VFS overlays, breaking the framework header resolution that use_frameworks! :linkage => :static (required by Firebase) relies on.

On new architecture, these issues are being patched upstream and worked around in our example app. On old architecture, they are not — and never will be. A client on old architecture cannot publish App Store updates without manually applying a private fork's worth of build patches (Float.h removal, ReactCommon header copies, FBReactNativeSpec framework aliasing, Yoga header copies, system-header cleanup, narrowing-error suppression, and more) — and rediscovering those patches with every Xcode 26 point release.

Practical reality: out-of-the-box, old architecture is no longer publishable to the App Store. Our own stance on still supporting old-architecture clients through Q3 2026 lives in the "Our SDK" column — but those clients face a non-trivial iOS build problem we cannot solve for them.

Client communication

Two client groups. Different urgency, but each only needs one clear message.

Clients on new architecture

On track

They're architecturally aligned but still using CocoaPods. No action right now — but as React Native and React Native Firebase ship full SPM support through 2026, they'll need to upgrade to pick it up before the December 2026 CocoaPods read-only date and the Q1 2027 Ometria SDK minimum-version cutover.

Ready-to-send message 
Hi [Client],

Quick heads-up on the React Native iOS migration happening across the ecosystem this year.

Your app is on React Native's new architecture — that's the right place to be. No urgent action needed right now, but a few things to keep on your radar:

• Since you use React Native Firebase: their Swift Package Manager (SPM) support is in preview. SPM is replacing CocoaPods as the iOS package system. Firebase stops publishing to CocoaPods in October 2026 — update React Native Firebase to a version with SPM support by then.
• Keep your React Native version current: RN is finishing its iOS migration to SPM. CocoaPods goes read-only on December 2, 2026 — by then you'll need an RN version with full SPM support.
• From Q1 2027, new Ometria SDK iOS releases will require RN and React Native Firebase versions with full SPM support.

Your current Ometria SDK integration doesn't need any changes today. We'll keep you posted as the ecosystem evolves.

Best,
The Ometria team

Clients on old architecture

Migrate now

Already past the Apple Xcode 26 deadline (April 28, 2026): old architecture doesn't compile out of the box, and only ships to the App Store via manual private patches. Firebase removes CocoaPods support in October 2026.

Clients on very old React Native (≤ 0.75) face two upgrades in one (React Native version + architecture) and should be flagged for immediate attention.

Ready-to-send message 
Hi [Client],

Your iOS App Store updates need a one-time migration to keep shipping cleanly. Here's why, and what's involved.

Since April 28, 2026, Apple requires Xcode 26 for every App Store submission. Your app uses React Native's old architecture, which doesn't compile cleanly on Xcode 26 — and the React Native team dropped old architecture entirely in June 2025, so no upstream fix is coming. The migration, done in one effort:
1. Move to React Native's new architecture
2. Upgrade React Native to the latest stable version (0.85+)
3. Upgrade to a current Ometria SDK release

• Since you use React Native Firebase: their Swift Package Manager (SPM) support is in preview. SPM is replacing CocoaPods as the iOS package system. Firebase stops publishing to CocoaPods in October 2026 — update React Native Firebase to a version with SPM support by then.

On the Ometria SDK side: any release we ship through end of Q3 2026 continues to support old architecture. After that date, new Ometria releases are new-architecture only. Existing Ometria SDK versions remain installable, but no longer receive new features or fixes.

If a client stays on old architecture — what gets frozen

A client who refuses to migrate keeps a working app, but the entire stack stops moving forward. Here's exactly what gets locked in place and when.

⚠ Active since April 28, 2026 — old architecture is effectively unpublishable to the App Store out of the box. Apple requires Xcode 26 + iOS 26 SDK for every submission and update. Old-architecture React Native does not compile on Xcode 26 out of the box, and there are no upstream fixes coming. A client on old architecture can only ship updates by manually maintaining a private fork's worth of build patches — and rediscovering them with every Xcode 26 point release. This is now the most immediate blocker, ahead of the Firebase and CocoaPods deadlines later in the year.

Action plan

Internal SDK team milestones, by phase.

Now — independent of anyone else Q2 2026

  • Publish the Expo support release (v2.8.0). Code is ready, no external blockers.
  • Announce the cutoff date for old-architecture support. Recommended: end of Q3 2026. Any release we ship up to that date supports old architecture; releases after that date drop it. (We're committing to a date, not to a specific release on that date.)
  • Sort clients by where they stand (see "Client communication" above). Identify who needs an early migration push.
  • Write the client message using the two groups in the Client Communication section above.
  • Prepare the SPM-mode release on a branch. Validate it against React Native Firebase's preview branch so we're ready to ship the moment they do.

When React Native Firebase ships their SPM fix Q3–Q4 2026

  • Ship our SPM-mode release. Most of the static-framework pain goes away for clients in one release cycle.
  • Update the Expo plugin to use the new linking mode.
  • Remove most of the Xcode 26 workarounds we've been carrying. One small workaround remains.

When React Native ships its full SPM move Later 2026 → Q1 2027

  • Bump Ometria SDK major version with minimum-version requirements: React Native with full SPM support + React Native Firebase v26+ (SPM-capable). Tentative: Q1 2027.
  • Eliminate the linking-mode setting from the project entirely.
  • Move off CocoaPods completely.
